# Seed data

Everything the fakes serve lives in `fake_data/` as plain JSON, meant to be edited by hand. The
names are fictional on purpose: real vendor names never appear next to fabricated numbers. Keep it
that way when you add data.

```
fake_data/
  seed/            copied into db/ on the DB's first start (or POST /admin/reset)
    services.json  providers.json  llms.json  offerings.json  load_profiles.json
    runs.json  run_results.json          generated by scripts/generate_seed_runs.py (§5)
  profiles/
    offering_profiles.json               latency and error model per offering (§3)
    service_profiles.json                prompt and response sizes per service (§4)
  blazemeter/*.json, splunk/*.json       response templates (see fakes.md)
  db/, blazemeter/state/, splunk/events/ live state, git-ignored (`make reset-data` deletes it)
```

The design shows on purpose:
- one LLM is served by several providers, at different prices and speeds;
- two services restrict which offerings they may use;
- one offering is `degraded` and one is `unavailable`;
- the open-weight models are only on cloud and inference-host providers.

## 5. Seed run history (`seed/runs.json`, `seed/run_results.json`)

`scripts/generate_seed_runs.py` writes 133 completed runs and their results. It runs the same
latency model as the live fakes through an offline virtual-user simulation, then aggregates the
output with the real `build_results`. It is deterministic: `random.Random(20261005)` is shared
across all runs, in plan order.

**The plan.** Times are in days before `END = 2026-10-05T18:00:00Z`.
- For each service, in seed order, with `pool` = its usable offerings (allowed and not
  `unavailable`):
  - for each offering `i` in the pool:
    - a fixed `baseline` run at `3 + 0.1·i` days;
    - a fixed `smoke` run at `9 + 0.1·i` days;
  - an auto `baseline` run over the whole pool at 2.5 days;
  - an auto `smoke` run over the whole pool at 8.5 days.
- For the flagship service `summarize-profile`, each of `aurora-api--aurora-4`,
  `stratus--aurora-4`, `cloudhaven--gale-3`, `northwind-api--gale-3`, `swiftserve--forge-70b` and
  `aurora-api--aurora-4-flash` (index `i`) gets:
  - a fixed `stress` run at `1 + 0.1·i` days;
  - an older fixed `baseline` run at `16 + 0.1·i` days, which gives the leaderboard's recent-runs
    lists some history.
- One more: an auto `stress` run at 0.8 days.

**Each run `n`** (in plan order):

| Field | Value |
|---|---|
| id | `r_seed{n:04d}` |
| batch_id | `b_seed{n:04d}` |
| label | `"Nightly benchmark"`, or `"Peak-load check"` for stress runs |
| started_at | `END − days_ago − duration_s` |
| created_at | `started_at − 30 s` |
| ended_at, updated_at | `started_at + duration_s + 20 s` |
| status / progress | `completed` / 100 |
| blazemeter | `{test_id: master − 1, master_id: 10 000 000 + 7n, report_url: null, status: "ENDED"}` |
| splunk | `{sid: "seed_<id>", search: "search index=llm_api run_id=<id>", search_url: null, events}` |
| headline | computed from the results |

**The simulation (per run).** Each virtual user `i` starts at `ramp × i / conc`, and the users are
processed in time order with a heap. For each request at time `t < duration`:
1. `active = min(conc, int(t / ramp × conc) + 1)` (or `conc` with no ramp-up).
2. The offering is the fixed one, or `pick_offering(pool, rng)` for auto runs.
3. `simulate_request(...)` produces the event.
4. Client response time = `e2e + uniform(25, 70) + expovariate(1/15)`.
5. The BlazeMeter sample is `(t, rt, ok, http_status)`.
6. The Splunk row is the event plus `run_id`, `service_id`, `routing`, `offering_id`, `provider`,
   `llm` and `concurrency`, with every value turned into a string and null as `""`.
7. The user's next request is at `t + rt / 1000 + think × uniform(0.7, 1.3)`.

The BlazeMeter report comes from the fake's own `_report` function, applied to those samples.

`runs.json` is sorted by `created_at`, and `run_results.json` holds `{id, **results}` for each run.

**After changing** the catalog, a profile or the plan: run `make seed-runs`, then
`make snapshot-fixtures` (to refresh the frontend's mock and contract fixtures), then
`make reset-data`. Every number after the change moves, because the runs share one random
sequence.
